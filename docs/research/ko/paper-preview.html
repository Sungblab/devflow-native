초록

AI 코딩 에이전트는 파일 탐색, 코드 수정, 테스트 실행, 리뷰 반영까지 점점 더 긴 소프트웨어 엔지니어링 작업을 수행한다. 그러나 현실적인 작업은 한 세션 안에서 끝나지 않는 경우가 많다. 세션이 종료되거나 컨텍스트가 압축되면, 다음 세션은 이전 세션이 어떤 파일을 왜 바꿨는지, 어떤 검증을 실행했는지, 어떤 위험이 남았는지 다시 추론해야 한다. 이 과정에서 반복 탐색, 토큰 비용 증가, 검증 누락, 허위 완료가 발생한다.

본 연구는 다중 세션 AI 코딩 에이전트를 위한 검증 인식 구조화 핸드오프를 평가한다. 제안 방식은 작업 목표, 현재 상태, 변경 파일, 결정 사항, 알려진 실패, gate evidence, 남은 위험, 다음 행동을 repo-local state로 기록하고 다음 세션에 전달한다. 비교 조건은 no handoff, raw transcript, token-matched free-form summary, artifact-only, structured handoff, gate evidence only, structured handoff plus gate evidence, human oracle handoff다.

1. 문제

“내 프로젝트 파악하고 이어서 해줘”라는 프롬프트는 큰 코드베이스에서 비싸다. 에이전트는 README, 패키지 설정, 소스 디렉터리, 테스트, 최근 git diff를 다시 읽는다. 이 탐색은 첫 유효 수정 전에 수만 토큰을 소모할 수 있고, 이미 알고 있던 실패나 미실행 gate를 놓치게 만든다.

긴 컨텍스트 모델과 세션 압축은 이 문제를 완화하지만, “무엇이 현재 작업 상태인가”와 “완료라고 말해도 되는 검증 근거가 있는가”를 자동으로 보장하지 않는다.

2. 핵심 아이디어

Devflow의 가설은 단순하다. 다음 세션에 raw transcript나 막연한 요약을 넘기기보다, 현재 작업 상태와 검증 증거를 정해진 schema로 넘기면 에이전트가 덜 헤매고, 검증 없이 완료를 주장할 가능성이 낮아진다. 

project contract
  -> slice spec
  -> implementation plan
  -> plan-bounded agent session
  -> gate evidence
  -> finish guard
  -> next-session handoff

제품 관점에서 Devflow는 코딩 에이전트가 아니다. repo-local black box recorder이자 continuity layer다. 연구 관점에서는 이 continuity layer가 실제로 에이전트 continuation을 개선하는지 검증하는 harness다.

4. 비교 조건

조건 설명 비교 목적
A. No handoff 원래 task와 현재 파일 상태만 제공 세션 단절 기준선
B. Raw transcript 이전 세션 대화/로그 전체 제공 정보량은 많지만 noisy한 조건
C. Token-matched summary structured handoff와 비슷한 길이의 자유 요약 구조화 효과 분리
D. Artifact-only changed files, git diff, command logs, gate outputs만 제공 파일/로그 노출 효과 분리
E. Structured handoff 정해진 schema로 상태 전달 구조화 자체의 효과
F. Gate evidence only 검증 결과와 위험만 제공 검증 증거 효과 분리
G. Structured handoff + gate evidence 제안 방식 최종 평가 조건
H. Human oracle 사람이 만든 최적 인수인계 상한선

5. 측정 지표

  • continuation success: acceptance criteria와 required gates를 만족했는가
  • false completion: 완료를 주장했지만 required gate가 실패/누락/unknown인가
  • token cost: 조건별 input/output token 또는 proxy log 비용
  • time to first useful edit: 첫 의미 있는 코드 수정까지 걸린 시간 또는 tool-call 단계
  • irrelevant file read count: gold context와 무관한 파일 읽기 수
  • repeated exploration count: 이전 세션이 이미 확인한 파일/명령을 다시 탐색한 횟수
  • handoff quality: completeness, faithfulness, minimality, actionability rubric 점수

6. 실험 설계

각 task fixture는 초기 prompt, 중단 시점 snapshot, acceptance criteria, required gates, gold changed files, gold context pointers, expected risks를 가진다. 첫 세션은 의도적으로 중간 상태에서 멈춘다. 두 번째 세션은 조건 A-H 중 하나의 continuation package만 받고 작업을 이어간다. gold next action과 hidden acceptance oracle은 평가자 metadata에만 남긴다.

성공 여부는 가능한 한 deterministic evidence로 본다. 테스트, 타입체크, lint, build, acceptance criteria, 실제 diff를 우선 사용한다. AI judge는 handoff quality처럼 의미 판단이 필요한 곳에서만 보조적으로 사용한다.

8. 결론 초안

Semble이나 CodeGraph 같은 token-efficient code search / code graph 도구는 관련 코드를 찾고 구조를 이해하는 비용을 줄여준다. 그러나 이전 세션의 작업 상태, 검증 증거, 완료 차단 요인을 다음 세션에 보존하지는 않는다. 따라서 이 도구들은 core A-H 실험 이후의 확장 baseline 또는 모든 조건에 동일하게 허용하는 controlled tool로 다룬다.

본 연구는 AI 코딩 에이전트의 장기 작업 문제를 일반적인 메모리 문제가 아니라, 세션 경계의 workflow-state handoff 문제로 좁힌다. Devflow는 repo-local event log, structured handoff, gate evidence, finish guard를 통해 다음 세션이 필요한 상태를 더 작고 검증 가능한 형태로 받도록 한다. 파일럿 실험의 목적은 이 구조가 실제로 continuation success를 높이고 false completion과 반복 탐색을 낮추는지 검증하는 것이다.
