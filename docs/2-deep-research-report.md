It changes the conversation from “is this an interesting product?” to “can this protocol support a defensible causal claim?”, which is exactly where serious SE/agent evaluation work now lives. Recent work increasingly treats the **harness, context representation, state surface, and memory protocol** as first-class scientific objects rather than treating the entire product stack as the contribution. The proposal is researchable and timely because it sits between three now-active lines of work: repository-level coding benchmarks, context/memory evaluation, and harness engineering. SWE-agent showed that interface design alone can materially change coding-agent performance; ContextBench and SWE-ContextBench showed that **what** context is surfaced and **how** it is represented matters, not just whether more context is available; and MemoryArena showed that persistent memory is still brittle in genuinely multi-session settings. ## Why this question is timely

Static repository guidance is now a real part of the coding-agent ecosystem. The AGENTS.md specification positions itself as a predictable place to store setup commands, tests, and conventions for agents, and the Codex documentation says Codex reads AGENTS.md files before it starts work in a run, building an instruction chain from global and project scopes. That makes AGENTS.md highly relevant—but also largely **static** and session-start oriented. It is useful for norms and repo conventions, but it is not designed to communicate active workflow state, unresolved failures, or what was actually verified in the last interrupted session. citeturn7view4turn17view0

The timing is also good because static context files are not a free win. A 2026 study on AGENTS.md found that repository-level context files often **reduced task success rates** relative to no context while increasing inference cost by more than 20%, and it concluded that unnecessary requirements can make tasks harder. That is directly relevant to your design: if you introduce a handoff artifact, reviewers will ask whether you are measuring the benefit of *structured, minimal, stateful continuity* or simply adding another context blob that sometimes hurts. citeturn8view2turn8view3

At the same time, the “generic memory system” framing is now too broad to be novel on its own. Hermes Agent already exposes bounded persistent memory, session search over prior conversations, and memory-provider integrations that persist information across sessions. MemoryArena goes further by benchmarking long-context, retrieval-based, and external-memory agents in sequential multi-session tasks, and it shows that even strong systems still struggle to maintain and reuse task state reliably over session boundaries. That makes your narrow framing much stronger than a broad “memory for agents” pitch. citeturn7view3turn12view2turn10view0

Representation quality is the real battleground. ContextBench found that coding agents often retrieve broadly, favor recall over precision, and leave a large gap between what they **explore** and what they actually **use**. SWE-ContextBench similarly found that correctly selected summarized experience improves resolution accuracy and reduces runtime and token cost, while unfiltered or poorly selected context can have little benefit or even negative effects. A separate 2026 compression paper showed that compressing repository context can reduce token budgets by roughly 52% to 71% while improving issue-resolution rates. Together, these papers strongly support your decision to study **state packaging** rather than “more context” in the abstract. citeturn14view0turn14view2turn19academia1turn8view4

## Where the design is most fragile

The single biggest internal-validity threat is **construction leakage**. In your own phrasing, the canonical interrupted snapshot includes a “gold next action.” If that gold action, or any post hoc diagnosis derived from seeing the final fix, leaks into D, E, or F, then you are no longer comparing continuation packages. You are comparing packages with different amounts of privileged answer information. This is exactly the kind of contamination that later SWE-bench analyses warn about when they discuss solution leakage, and it is precisely why the SLUMP benchmark introduced an **exposure audit** to check whether scored components are actually recoverable from the visible interaction rather than from hidden knowledge. citeturn15search3turn15search0turn13view2

The second major threat is a **representation confound**. If structured handoff wins, a reviewer will ask whether it won because it was structured, because it contained more task-relevant facts, because it contained better diagnosis, or because it included verification evidence. Your proposed A–G design is already much better than most early-stage student protocols because it separates no handoff, raw transcript, token-matched free summary, structured handoff, gate-only, and structured-plus-gate. But I would still expect reviewers to demand one more separation: a condition that exposes only the raw observable artifacts—changed files, git diff, command outputs, failing/skipped gates—without any narrative interpretation. Without that, a strong result can still be reduced to “you gave the agent the right files and logs.” citeturn14view0turn14view2turn12view0turn11view0

The third weak point is **label validity**, especially for false completion. SWE-bench itself already acknowledged that execution-based testing alone does not guarantee reliable evaluation, and later studies showed why: patches can pass tests while still diverging from the human-written solution or failing developer intent. In parallel, FixedBench shows the mirror-image problem: agents frequently make unnecessary code changes when the right action is inaction, and explicit “verify first” instructions can introduce an abstention failure mode when only a partial fix exists. So if your false-completion label is purely rule-based, it can still misclassify both semantically wrong successes and semantically wrong abstentions. citeturn18view2turn15search0turn8view6

The fourth issue is **ecological validity**. A canonical interrupted snapshot is not a naturalistic simulation of how real teams stop and resume work. But that criticism only bites if you oversell the benchmark. Benchmark papers routinely freeze repository state, environment, and verification conditions precisely to compare methods under controlled conditions: SWE-bench uses a fixed codebase snapshot, issue text, and test oracle; SLUMP freezes progressive interaction scripts; and SWE-Bench Atlas emphasizes strict reproducibility and environmental determinism during construction. The right defense is to frame this as a **controlled interruption benchmark** and then add at least one follow-up natural-interruption case study for realism. citeturn18view2turn13view2turn18view0

## Direct answers to your ten questions

**Question 1.** The largest internal-validity threat is **oracle leakage during snapshot and handoff construction**. If the same researcher creates the interrupted state, writes the structured handoff, defines the gold state, and knows the final fix, the structured conditions can silently contain privileged information. This is especially dangerous if “gold next action” exists anywhere outside evaluation metadata. The core remedy is an **observable-only rule**: every claim in a continuation package must be traceable to Session 1’s prompt, tool calls, file reads, file edits, git diff, command log, or gate outputs—never to hidden tests or the final gold patch. This is the cleanest lesson to borrow from the solution-leakage literature and from SLUMP’s exposure-audit logic. citeturn15search3turn15search0turn13view2

**Question 2.** Yes, the canonical interrupted snapshot can be criticized as unrealistic—but only if you present it as a simulation of day-to-day software work rather than as a controlled benchmark. Frozen states are normal in repository-level evaluation because they let you hold environment, codebase, and oracle constant while changing only the intervention. The best defense is to explicitly say: “This benchmark measures *resumption under controlled interruption*, not full workflow realism,” and then add a smaller ecological extension where Session 1 is naturally produced and interrupted mid-run. citeturn18view2turn13view2turn18view0

**Question 3.** Your A–G set is already strong, but one baseline is still missing: an **artifact-only package** that contains changed files, git diff, command log, and gate outputs without prose. That condition isolates whether narrative handoff structure matters beyond surfacing the right artifacts. I would not merge D and E, because separating workflow-state structure from verification evidence is analytically valuable. I would keep B as well, but only if you can define a consistent truncation or retrieval rule when transcripts exceed usable context; MemoryArena treats verbatim history as a distinct memory class, so it is still a meaningful comparator. citeturn12view0turn12view2turn14view0turn11view0

**Question 4.** A rule-based false-completion definition is necessary, but its weakness is that it will still miss **plausible but incorrect** completions and can also mishandle correct abstention. Wang, Pradel, and Liu showed that patches can pass tests and still diverge behaviorally from the ground truth, while FixedBench showed that agents often act when they should not, and can also abstain incorrectly when part of the issue is already fixed. So false completion should not be a single binary rule; it should be a label family that includes at least “unsupported completion,” “semantic mismatch,” and “wrong abstention,” with sampled human audit or differential testing on a subset. citeturn15search0turn8view6turn15search2

**Question 5.** A token-matched free-form summary is only fair if it is generated from the **same observable inputs**, with the **same tokenizer**, under a **fixed budget**, and without schema labels or privileged diagnosis. I would additionally require an evidence map: each sentence in the free-form summary must be traceable to logs, diff, or outputs. That matters because recent work repeatedly shows that context effectiveness depends more on representation quality than on raw quantity, and overbroad context can actively hurt. A useful sensitivity check is to compare both **raw-token parity** and **content-token parity** so that structured field names do not become an accidental confound. citeturn19academia1turn14view0turn8view2turn8view4

**Question 6.** A “human oracle handoff” is not a true upper bound unless you make its privilege explicit. In practice it is a **diagnostic ceiling** with at least four problems: it may include non-observable knowledge, it hides substantial annotation labor, it has inter-rater variability, and it is not directly deployable. The right analogy is the oracle-guided settings in SWE-ContextBench or the oracle-guided code distillation used to build compression data: useful for understanding what is possible, but not a fair product baseline. If you keep G, report its observability compliance, author time, and whether it was produced without looking at the final patch. citeturn19academia1turn8view4turn13view2

**Question 7.** For an undergraduate project or workshop paper, my practical minimum would be a **two-stage design**: first a 3-task smoke test to debug instrumentation, then a main study with **8 to 10 tasks and 3 repeats per condition**. Better would be **12 to 15 tasks with 3 repeats**, especially if tasks vary in failure mode. This exact threshold is an inference rather than a published field norm, but it is consistent with the scale of diagnostic long-horizon studies like SLUMP, which uses 20 tasks, while benchmark-construction papers operate at much larger scale. For your purpose, paired comparisons across the same frozen tasks matter more than raw task count alone. citeturn13view2turn19academia1turn14view0

**Question 8.** The phrases most likely to hurt you are “OS,” “agent memory system,” “solves long-horizon continuity,” “human-like handoff,” and “improves reliability across coding agents” without qualification. The literature is too clear that static context can backfire, current memory systems remain brittle, and agents still show severe action-pathology under verification ambiguity. The safest claim is a **controlled, task-bounded, interrupted-task continuation result**—not a general system claim. citeturn8view2turn12view2turn8view6

**Question 9.** The must-compare set is: **SWE-agent** for harness/interface effects; **Agentless** for a strong non-agent simplicity baseline; **AGENTS.md** plus the 2026 AGENTS.md evaluation paper for static repository guidance; **ContextBench** for process-level context metrics; **SWE-ContextBench** for summary/reuse settings and oracle/free reuse distinctions; **SLUMP/ProjectGuard** for long-horizon specification tracking and exposure audits; **MemoryArena** for multi-session memory evaluation; and **Hermes Agent** as a representative persistent-memory system. ## Related work and claim boundaries

The strongest way to position the paper is to say that it sits **between** static instruction files, generic memory systems, and repo-retrieval work. AGENTS.md and Codex’s AGENTS.md pipeline establish that project-specific instructions are now a normal part of coding-agent practice, but they are loaded before work begins and are primarily about durable guidance rather than active task state. Hermes exemplifies persistent cross-session memory and session search, but it is intentionally general-purpose. RepoGraph, RepoUnderstander, and Semble all target repo navigation or retrieval efficiency. Your contribution should therefore not claim novelty in “memory,” “repo understanding,” or “agent scaffolding” in general. It should claim novelty in the **evaluation and representation of interrupted-task handoff state plus verification evidence**. citeturn17view0turn7view4turn7view3turn11view0turn11view1turn11view2

The most review-resistant framing is also the least glamorous: this is **not** an operating system, a universal memory architecture, or a theory of long-term agent cognition. It is a controlled study of whether a specific handoff representation helps a coding agent resume an interrupted task under shared filesystem state. That narrower framing is exactly what makes the work defendable. Papers like SWE-agent, ContextBench, MemoryArena, and Natural-Language Agent Harnesses succeed because they isolate one leverage point—interface, retrieval process, memory use, or harness representation—and evaluate it cleanly. citeturn8view7turn14view0turn10view0turn16view0

## Priority modifications

1. **Remove “gold next action” from every evaluated continuation package and introduce an observable-only audit.**  
   Gold next action should exist only in hidden evaluation metadata. Add a per-field provenance check so every handoff claim can be traced to Session 1 artifacts. This is the single highest-value correction because it directly attacks the biggest internal-validity threat. citeturn13view2turn15search3

2. **Add an artifact-only baseline and consider splitting structured handoff into observable versus interpreted forms.**  
   A narrative-free artifact bundle will tell you whether narrative structure adds anything beyond surfacing the correct files and logs. Splitting “structured handoff” into observable-only and interpreted versions will let you test whether diagnosis itself is the causal ingredient. citeturn12view0turn14view0turn11view0

3. **Upgrade false-completion labeling beyond pass/fail gate logic.**  
   Keep the rule-based core, but add sampled manual audit, hidden or strengthened tests where possible, and a separate label for wrong abstention. Otherwise you risk counting semantically wrong patches as successes and semantically wrong refusals as prudence. citeturn15search0turn15search3turn8view6

4. **Pre-register the generation protocol for the token-matched free summary and the expert-authored ceiling.**  
   Fix the tokenizer, token budget, generator settings, evidence sources, and annotator blindness before running the experiment. For the human ceiling, report creation time and whether the author was allowed to inspect only visible Session 1 evidence. This will preempt fairness objections. citeturn19academia1turn8view4turn13view2

5. **Run a staged pilot rather than jumping straight to a full matrix.**  
   Start with 3 tasks to debug instrumentation, then move to at least 8 to 10 tasks with 3 repeats for a workshop-scale result. Use paired comparisons on the same frozen interruptions and report uncertainty intervals, not just mean scores. That is the smallest design that still looks like disciplined evaluation rather than a demo. citeturn13view2turn19academia1turn18view2
